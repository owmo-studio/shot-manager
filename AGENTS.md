# OWMO Shot Manager — agent guidance

## Purpose and scope

OWMO Shot Manager is a single-user, local macOS Electron app for reviewing original video footage from cards and folders, editing per-shot attributes, and processing selected footage into a canonical NAS Library. Processing encompasses destination placement, associated assets, metadata, and required transformations; the implementation prepares local ProRes proxies, transfers originals/thumbnails/missing proxies, and publishes JSON last. It manages an active working library, not an archive.

The current priority is to complete and validate Import using isolated dummy sources and destinations. Library browsing/editing, NAS-to-local Edit sync, editor-specific layouts and deletion are deferred. Discuss those features before implementing them.

Read the relevant code and `README.md` for current behavior. Treat this file as durable constraints, not a complete product specification. If older documentation conflicts with working code or a new user instruction, resolve the discrepancy before changing behavior.

## Non-negotiable safety

- Source footage is read-only. Never rename, delete, overwrite, transcode, or reorganize original media as part of discovery, inspection, or testing.
- Never read, write, or mutate real NAS media during prototyping without explicit authorization for that operation. Use temporary dummy folders and synthetic media in automated tests. A configured Library path alone does not authorize NAS access.
- Before any future Library write, validate the configured destination and mounted volume. A missing SMB mount must never turn into a write to its empty local mount-point directory. Do not use example paths as defaults.
- Preserve corrupt or unreadable persisted state and report the error; do not silently replace it. Keep destructive local-data operations explicitly confirmed and confined to recognized app-owned files.
- Backend filesystem routes accept validated asset identifiers, never arbitrary renderer-supplied paths. Keep Electron's preload restricted and the backend bound to authenticated loopback access.

## Architecture and data

- Keep the existing Electron/electron-vite, React/TypeScript, Fastify, and `shared/` structure. The backend runs as a separate Electron utility process; renderer reloads must not own or cancel backend jobs. Avoid new services, databases, or dependencies without a concrete need.
- Inspect each original video independently. Source-derived technical metadata is read-only; unknown or conflicting values remain explicit. Do not infer device, codec, color, or capture date from folder names, camera proxies, or external XML. Playback and previews use originals; cached thumbnails are disposable.
- All assigned attributes (Identity, Project, Scene, Notes, and Tags) are optional, including when processing clips. Persist Identity/Project options; keep Tag suggestions as a session-only list of tags used by loaded clips while preserving tags in clip drafts. Keep editing selection distinct from the current skip state: discovered clips are included by default, and an explicit skip excludes them from future processing and persists in the fingerprint-keyed local draft. Clearing attributes preserves Skip. Do not reintroduce a separate processing checkbox. See the code and `README.md` for interaction details.
- Library choices in Configuration remain pending until Save. Cancel, close, and Escape discard pending choices. Cache storage is app-managed under the local app data directory; there is no Cache location setting.
- Configuration Identity/Project deletions clear only the matching field and cascade to all saved local clip drafts, including offline records, after an affected-clip review distinguishing active and saved records. Unused entries need no extra confirmation. Apply atomically, preserve unrelated attributes, reject stale reviews/scan conflicts, and update loaded clips without rescanning. This does not authorize changes to source footage or Library files.
- After confirmation, Revert restores the five descriptive attributes from selected pending clips’ metadata JSON in the validated configured Library into local drafts atomically. Preserve Skip, thumbnails, and processing receipts; reject missing, invalid, mismatched, or symlink metadata and concurrent local edits without partial restoration. This explicit action reads only the selected metadata files and never writes Library assets.
- Local drafts, configuration, fingerprint records, and disposable previews have different reset semantics. `Clear Cache` confirms selective deletion of app-owned metadata, thumbnails, fingerprints, and proxies, with keep checkboxes for each category. It preserves the saved Library location, source footage, and Library assets. Browse Cache opens the app-managed folder in Finder. The Library location X stages clearing its setting for Save. Previous user-chosen Cache files are preserved when switching to app-managed storage; do not delete them automatically. After 90 days without use, clip drafts (including synced receipts), thumbnails, valid fingerprint records, and cache proxies expire during graceful shutdown. Saved Identity/Project options and corrupt persisted records remain until explicit clearing. Clearing selected clips' attributes or removing vocabulary entries has narrower effects.
- Publish clips only after fingerprint and attributes are ready; use the fingerprint as the clip ID across selection, editing, and asset lookup. Keep file locations separate. The backend workspace owns one record per fingerprint with one active absolute file path/identity; scan jobs do not own clip records or thumbnail lifetimes. Repeated/overlapping discovery keeps a valid active path and current edits, or adopts a freshly fingerprinted matching copy when the old path is unavailable. Never switch a queued Commit’s captured path before completion/cancellation. Discovery provenance fields and legacy backend source endpoints remain internal compatibility details; the renderer has no Source list, source filters, source rescan/remove/re-link API, or source-owned clip state.
- A sampled fingerprint associates local drafts/previews with matching media and is the Library ID; it is not proof of duplicate content or transfer integrity. Successful rsync completion is the accepted transfer-success criterion; do not add a separate full-file SHA-256 pass.

## Agreed Library storage

- Start with a flat Library: `<full-lowercase-sampled-fingerprint>.<role>.<ext>`. Reserved roles are `source`, `thumb`, `metadata`, and `proxy`, with one published asset per role per shot initially. Preserve the source's original format extension, normalized to lowercase; generated assets use their actual format's extension. Preserve the original source filename in metadata JSON.
- Processing places a copy of the original video, the current generated or assigned thumbnail, a ProRes proxy if missing, and metadata JSON in the Library. Always include every attribute field, even when empty: `identity: null`, `project: null`, `scene: ""`, `notes: ""`, and `tags: []`. The JSON also preserves source/technical metadata, date evidence/confidence, and processing completion information; see `README.md` and the implementation for the field contract.
- The app generates ProRes 422 Proxy MOV files; other software may add derived assets. Discover optional assets by fingerprint and role; no separate asset-inventory manifest or centralized database is required. Keep the internal contract simple; schema versioning and multi-writer coordination machinery are not required. Assume existing regular Library proxy filenames are good; leave them and other additional assets untouched during processing.
- Readers ignore temporary/partial filenames. Let rsync use its temporary-file-and-rename behavior; do not expose an in-progress transfer under its final filename. Publish metadata JSON atomically and last, after source, thumbnail, and any missing proxy transfers succeed. Existing JSON during a replacement describes the previous completed version until replaced.
- Future browsing should use a disposable local catalog backed by the Library files. Avoid unnecessary per-asset inspection during catalog discovery. Centralize relative-path construction so fingerprint-prefix buckets can be introduced later if measured SMB performance warrants them; do not implement buckets now.

## Agreed processing queue

- Eligible clips are not skipped, already queued, or synced in their current state. Each must have an available source video and a ready generated or assigned thumbnail; missing attributes do not block processing. Enable Commit when the candidate list is nonempty and ready. Validate the configured Library destination and mount before execution.
- Commit opens a simple confirmation with count, total size, and a scrollable clip list marked New or Update. Informational tags are neutral blue; a Proxy tag appears only when a cache or Library proxy is available, including if preparation finishes during review. An X excludes and dims a row in this submission, then changes to a dash that restores it when clicked; excluded rows remain visible and saved Skip is unchanged. Cancel makes no queue changes; Commit authorizes queueing and replacement for the included rows. Detect existing fingerprint matches during review and recheck before writing; a newly discovered conflict requires a decision rather than an unreviewed overwrite.
- Capture an immutable in-memory snapshot of each accepted clip's source, thumbnail, attributes, and destination. Lock waiting and processing clips against edits and execute from the snapshot. Folder discovery may continue during Commit. Eject can cancel selected queued/active clip jobs after confirmation without stopping unrelated work; Commit appending remains deferred. Use one transfer worker and one independent proxy encoder concurrently. Submitted clips get encoding priority, and ready clips transfer without waiting behind clips still encoding. Backend work survives renderer reloads. Internal byte-weighted source/thumbnail/proxy transfer progress stays below 100% until metadata publication, receipt persistence, and completion cleanup succeed.
- The footer application indicator reports one highest-priority issue (red for configuration/communication failures or an unavailable Library, yellow for unavailable media or proxy work), newest among equal priorities, or green Ready only after successful checks. Its lightweight health checks may inspect the configured Library folder/mount and permissions; do not poll asset inventories or open media. Cache errors surface through background work, not a configured-location check.
- Adding folders through buttons or drag and drop is unavailable while the application indicator reports a critical (red) issue such as Library Not Set. The empty workspace reflects that issue rather than claiming readiness. Yellow warnings do not by themselves block adding sources.
- The footer always shows overall task progress at its idle height: one equally weighted task per needed proxy encode and submitted clip transfer, with partial progress and only the total task count remaining beside the bar. Include background proxy work before Commit; existing proxies add no encoding task. Retain completed tasks until fresh work starts after idle, grow the total when work is added during a session, and remove cancelled/skipped/failed unfinished tasks. The footer has no cancellation control; the toolbar Stop cancels all queued and active work. Card style communicates Discover/Editable/Queued/Active/Synced/Change: discovery is locked until thumbnail preparation completes, background encoding alone never locks metadata, queued cards dim and subtly animate, active transfers show a centered spinner, synced cards have prominent green backgrounds and changed cards yellow backgrounds, with matching green/yellow outlines only when selected. Skipped cards are nearly black with heavily darkened thumbnails, muted filenames, and a deep red SKIP ribbon across the thumbnail’s top-left corner, but remain editable. Other card states need no visible badges/text. The independent undimmed top-right proxy indicator is hollow white while generation is queued or encoding, solid yellow when only in Cache, solid green when observed in the Library, and otherwise absent, with explanatory hover/accessibility text. Active proxy encoding shows a large centred yellow spinner matching the transfer spinner’s size; transfers take precedence. The thumbnail progress bar is yellow for proxy encoding and green for Library sync, without visible numbers; transfer activity takes precedence. Background encoding does not override the card’s underlying Library state.
- Use rsync for the source, thumbnail, and missing proxy. Preserve source modification times and use rsync's size/mtime quick check to avoid recopying unchanged files; existence alone is insufficient. Metadata-only changes should update JSON without recopying unchanged video. A successful transfer followed by successful JSON publication completes processing.
- Persist the last successful processing state alongside the fingerprint-keyed local draft, including the Library destination and the attributes/thumbnail state needed to recognize changes. Show Synced for a clip matching its last successful processing state and exclude it from subsequent submissions. Attribute or thumbnail changes show Needs Syncing and make it eligible again; Skip and editing selection do not invalidate sync state. Recognize reverted edits when they match the last successful state. Check Library asset filenames on startup, destination changes, before review, and explicit refresh, without polling asset listings or opening media/JSON contents. Synced requires the source, thumbnail, metadata JSON, and proxy to be present. Missing assets make the clip eligible again; a fully deleted clip is New. Existing core Library assets without a matching receipt, or with an incomplete asset set, show Needs Syncing and are reviewed as Update; genuinely new clips remain neutral. Preserve receipts and show unverified status if the Library cannot be checked; never treat an unavailable share as empty. This presence check does not verify file contents.
- The toolbar control beside Configuration is Refresh when idle/paused and an animated activity ring while transfer or background work exists, revealing a red Stop square on hover or keyboard focus. Respect reduced-motion preferences. Refresh checks Library/cache presence and resumes missing thumbnail/proxy generation only; cancelled Library submissions require Commit again. Stop all work confirms before cancelling thumbnail/proxy FFmpeg jobs and rsync, clearing queues, and suspending automatic generation. A late refresh completion must not restart stopped work. Commit refreshes Library/cache presence and resumes required preparation before review, with transfers starting only after confirmation. A late Commit review must not restart work after Stop. The toolbar Stop is the only cancellation control. Completed Library clips, prior receipts, pending changes, and completed cache proxies survive cancellation. No standalone background-work footer control is needed. Never mark cancelled work synced; Library orphan cleanup remains deferred.
- Cache is managed under the local app data directory in a `Shot Manager Cache` folder with category subfolders, beside Electron's own `Cache` folder. It is not a user-configured or monitored location. Start the new Cache empty; leave files in the former shared `Cache`, older `owmo-shot-manager`, and previously user-chosen locations untouched. Generate only missing proxies after the Library filename check; reuse completed cache proxies by fingerprint. Use ProRes 422 Proxy MOV, 10-bit 4:2:2, 1280-pixel maximum long edge without upscaling, preserved display aspect/orientation, locked frame timing/timecode and audio channelization. Do not bake viewing LUTs or invent color declarations; camera-specific color evidence stays in JSON. Limit encoding to one lower-priority worker behind thumbnail preparation. Publish cache outputs by rename only on success, guard free space and folder identity, and delete matching cache proxies only after successful Library publication and local receipt persistence. No quota, database, or durable proxy journal is required. Clear Cache preserves whichever app-owned categories the user selects to keep.
- On failure, show a dialog identifying the clip and available error details, remove and unlock that entry, and continue the remaining queue. Preserve any previous successful processing record. Retained failed entries, retry workflows, and orphan cleanup are deferred.
- The queue is not persisted. An application crash or restart discards unfinished queue work; no durable journal, automatic resume, or recovery workflow is required. Usual local draft persistence and successful-processing state survive. A renderer reload is not an application restart and must not cancel backend work.
- Use dry-run plans and fault tests on dummy folders before requesting authorization for any real NAS write.

## Clip-centric workspace and Eject

- The left panel contains the workspace clip count, Add Clips, and per-clip device filters. There is no Source list, source filtering, source rescan/remove/re-link control, or Devices heading. Adding a folder through + or drag and drop starts additive discovery, including while a Commit runs. Temporary scan progress and concise errors appear above the grid.
- Clips remain fingerprint-keyed with one active absolute file path/identity. Re-adding a file leaves its card unchanged; a newly fingerprinted matching copy replaces an unavailable path, preserving drafts, receipts, and custom thumbnails. Queued Commit paths stay fixed. Discovery jobs never own workspace membership or thumbnail lifetimes.
- A card Eject icon and inspector single/bulk Eject actions remove selected clips from the workspace. Skip retains context and excludes processing; Eject changes membership. Ordinary Eject is immediate, including cancellation of background encoding/preparation. Queued or actively transferring clips require one confirmation for the selected set, rechecked by the backend. Settle only their thumbnail, encoder, and transfer work before removal; unrelated clips continue. Preserve original footage, Library assets, cached attributes/Skip, successful receipts, and completed cache proxies. Publication racing with cancellation must retain the successful receipt before removing the card.
- Metadata locks do not prevent selecting queued/active cards for Eject. Mark ejecting records unavailable for new edits, Commit snapshots, and generation. Late discovery/thumbnail/encoder callbacks must not resurrect ejected cards; scan-generation exclusions last until an explicit later folder addition can admit the fingerprint again.
- Keep a non-visible, derived list of actual clip-containing directories and poll only whether each directory exists. No selected-root monitoring, mounted-volume detection, directory-content rescans, or periodic inspection of all child videos. Stop monitoring a directory when its final workspace member is removed. Individual access still validates file path/identity; directory recovery revalidates affected files and respects manual Stop.
- A missing directory flags its associated clips and produces one consolidated path/affected-count warning per outage, offering Eject affected clips. Retain cached information and metadata editing. Disappearance never ejects clips automatically. Unaffected work continues; unavailable queued clips retain the current failure/removal behavior and require Commit again after recovery.
- Clear Cache restarts the backend with a transient main/backend handoff of surviving file paths, unfinished discovery, and Eject exclusions, then reloads the renderer. Never rescan completed discovery roots and silently restore ejected siblings. This handoff is only for explicit Cache clearing; workspace membership and unfinished queues are not persisted across application restarts/crashes.

## Remaining flexible queue discussion

- Keeping Commit available to append reviewed clips during another Commit remains deferred. Single/bulk Eject and per-clip cancellation are implemented; the toolbar Stop still cancels all queued and active work.
- Before implementing appendable Commits, settle concurrent review/replacement conflicts, task counts as submissions expand, and whether unavailable queued work should wait instead of following the current failure policy. Preserve explicit authorization and immutable accepted snapshots, and validate with isolated dummy media/destinations.
